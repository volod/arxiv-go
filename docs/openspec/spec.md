# arxiv-go Product Specification

## Purpose

`arxiv-go` builds `arxgo`, a single-file command-line utility that separates video files from a
large mixed file archive. Video files consume most of the space in such archives and make sharing
the document part difficult. `arxgo` lets an operator keep documents on a local disk while video
files live in a separate video archive (another disk, a network share, and later cloud storage),
without losing the link between a document folder and the videos that belonged to it.

The utility:

1. traverses an archive and writes a CSV registry of every file, marking binary, media, picture,
   video and large files;
2. moves video files into a video archive that mirrors the original directory tree, leaves a
   video description file with a link at each original location, and writes a video registry;
3. restores the video files into the main archive, optionally recreating deleted directories;
4. (stage 2) creates short video samples and still frames for quick viewing;
5. (stage 3) publishes the video archive to Google Drive or Microsoft SharePoint.

This specification is living. Product behavior, boundaries and evaluation belong here and in the
stage pages it links. Remaining work belongs in the [implementation plan](../impl/plan.md);
delivered behavior is indexed by [current implementation](../impl/current.md). The
[architecture](architecture.md) describes packages, data flow and transaction design.

## Scope

In scope:

- Local and network-mounted filesystems on Linux and Windows (amd64). Both are implemented;
  only Linux is tested as a gate (see [development integrity](#development-integrity)).
- One archive root and one video archive root per run.
- File-level and media-level metadata for the registry and the video descriptions.
- Crash-safe, resumable, idempotent split and restore of arbitrarily large archives.
- Stage 2: previews generated by an external `ffmpeg` process.
- Stage 3: upload of the video archive through documented cloud REST APIs.

Out of scope:

- Transcoding or re-muxing the original video files. Originals are moved or copied byte-for-byte.
- Deduplication, content classification beyond file type, and editing of document files.
- A GUI, a daemon mode or a database server.
- Moving non-video media (audio, pictures). They are registered but stay in place.
- Hardlinks, reflinks or symlinks as a placement strategy; the video archive holds real files.

## Design principles

1. **Originals are sacred.** A source file is removed only after its copy is durably written and
   verified. No operation overwrites a different file without an explicit flag.
2. **Every mutation is a transaction.** File operations are journaled in a write-ahead log before
   they happen; an interrupted run is rolled forward or back from the log, never guessed.
3. **Resumable by default.** Rerunning the same command after a crash continues the run; rerunning
   it after success is a no-op that reports nothing to do.
4. **Fail before work.** Argument validation, tool availability and free-space checks run before
   the first mutation.
5. **Single static binary.** The executable is built with `CGO_ENABLED=0` and runs without an
   installer, runtime or shared library. A feature that needs a capability neither the Go standard
   library nor a pure-Go dependency provides is either delegated to a bundled or installed external
   tool (`ffprobe`, `ffmpeg`) or not implemented.
6. **Deterministic outputs.** Traversal order, CSV row order and file names are
   stable for the same input, so reruns and diffs are meaningful.
7. **Observable.** Progress and balanced statistics are logged at a bounded rate; every run leaves
   a machine-readable log and a final report.

## Cross-cutting rules

### Platforms and build

- Go 1.27 or newer; module `github.com/volod/arxiv-go`; binary `arxgo` (`arxgo.exe`).
- Release builds: `CGO_ENABLED=0 go build -trimpath -ldflags "-s -w -X ...version=..."` for
  `linux/amd64`, `windows/amd64`.
- `make build` writes the Linux amd64 executable to `bin/arxgo`; `make build-all` writes that
  same Linux executable to `bin/arxgo` and the Windows amd64 executable to `bin/arxgo.exe`.
  The two targets must use the same Linux build recipe, and a clean checkout must build without
  first creating `bin/`.
- Platform-specific code uses build-tagged files (`*_linux.go`, `*_windows.go`, `*_unix.go`) and
  `golang.org/x/sys` only; no cgo.
- Paths in outputs use forward slashes and are relative to the owning root. Windows long paths,
  drive letters and UNC shares are supported for inputs.

### Dependencies

Runtime dependencies must be pure Go and statically linkable. Approved candidates:

| Dependency | Use | Stage |
| --- | --- | --- |
| [`github.com/gabriel-vasile/mimetype`](https://github.com/gabriel-vasile/mimetype) | Signature-based MIME detection with text/binary hierarchy | 1 |
| [`github.com/abema/go-mp4`](https://github.com/abema/go-mp4) | ISO BMFF (MP4, M4A, M4V, MOV, 3GP) box parsing | 1 |
| [`github.com/google/uuid`](https://github.com/google/uuid) | Pure-Go indirect dependency of `go-mp4` | 1 |
| [`golang.org/x/sys`](https://pkg.go.dev/golang.org/x/sys) | Free-space and device identity syscalls | 1 |
| [`github.com/joho/godotenv`](https://github.com/joho/godotenv) | Parse the optional `.env` file next to the executable ([environment file](stage-1-core/cli.md#environment-file)) | 1 |
| `golang.org/x/oauth2` | OAuth 2.0 token flows for cloud targets | 3 |

[`github.com/h2non/filetype`](https://github.com/h2non/filetype) was considered; `mimetype` is
preferred because it exposes a MIME parent hierarchy that answers `is_binary` without a second
table. Adding any other dependency requires a spec amendment. CLI parsing uses the standard `flag`
package, and `.env` parsing uses `godotenv` (read-only; it never changes the process environment).
Logging uses `log/slog`.

### External tools

`ffprobe` and `ffmpeg` are optional external executables, looked up first in the directory of the
`arxgo` executable and then on `PATH`. They are invoked through `os/exec` with argument vectors
(never a shell). When a requested option needs a missing tool, `arxgo` logs which options are
unavailable, prints the download link for the running `GOOS/GOARCH`, and exits with code 3 before
any mutation. Details: [tool discovery](stage-1-core/metadata.md#tool-discovery).

### Reserved paths

`arxgo` owns these names and excludes them from traversal:

- `<root>/.arxgo/` in either root: run lock, state, write-ahead logs, checkpoints and run logs.
- `<archive>/arxgo-registry.csv`, `<archive>/arxgo-videos.csv` and
  the same names inside the video archive root.
- Temporary transfer files ending in `.arxgo-part`, and preview part files named
  `<stem>.arxgo-part.<ext>` (a single extension after the marker).

### Operations and defaults

| Operation | Default | Mutates | Stage |
| --- | --- | --- | --- |
| `scan` | yes | registry output only | 1 |
| `split` | no | moves videos, writes descriptions and registries | 1 (previews: 2, upload: 3) |
| `restore` | no | moves videos back, removes or keeps descriptions and previews | 1 (previews: 2) |

The full contract is in the [CLI specification](stage-1-core/cli.md).

## Development integrity

[AGENTS.md](../../AGENTS.md) defines the task cycle; the
[planning workflow](../guide/planning-workflow.md) defines task shape, lanes and records.

- Permanent records under `docs/impl/records/` keep the full accepted task text, amendments,
  decisions and evidence. Current pages describe available behavior and link records. The plan
  holds only unresolved work.
- Implementation tasks add tests for integrity, correctness and business logic: the happy path,
  the main corner cases, and a regression for each defect found. Tests are deterministic,
  network-free and create their fixtures in `t.TempDir()`. No committed binary media fixtures:
  media fixtures are generated by test helpers (hand-built ISO BMFF boxes) or, for ffmpeg-backed
  tests, skipped with a logged reason when the tool is absent. GitHub CI does not install
  ffmpeg; live ffmpeg/ffprobe tests run only locally.
- Keep package unit and white-box component tests beside their Go code as `*_test.go`. Put
  cross-package integration tests, end-to-end tests, external test applications, reusable test
  helpers and committed mock or golden data under root-level `test/`. Use `test/testdata/` for
  static data, which Go ignores as a package. A test that needs private package hooks stays local;
  a new black-box integration proof belongs under `test/integration/`. See the
  [test layout](../../test/README.md) for paths and commands.
- Test gates run on Linux (amd64) only: unit tests, integration proofs, declared runs and CI.
  Windows support is still implemented and must cross-compile and type-check on Linux
  (`make build-all`, `make vet-windows`, both in `make ci`). Windows-only tests skip elsewhere and
  are never acceptance evidence. Runtime checks on a Windows host form the deferred
  [Windows verification scenario](../guide/windows-verification.md), outside the current
  development scope.
- A numeric coverage percentage is diagnostic, never a gate.
- Each stage ends with a checkpoint task that reviews the stage's cross-module invariants before
  the next stage starts, and an end-to-end proof on a generated archive.
- Tests that mutate real archives are never run by CI; operator trials are human-gated tasks.

## Evaluation and acceptance

| Gate | Evidence |
| --- | --- |
| Build | `make ci` passes on Linux, including the Windows cross-build and Windows vet; CI passes on `ubuntu-latest` |
| Registry correctness | Golden rows for a generated tree covering every flag combination and edge case in [registry](stage-1-core/registry.md#edge-cases) |
| Transaction safety | Crash injection after every WAL step, followed by resume, yields no lost, duplicated or partial files |
| Round trip | `split` then `restore` on a generated archive reproduces every original path, size and SHA-256 |
| Space refusal | Preflight with a simulated free-space value below the requirement exits 4 without mutation |
| Missing tools | Requesting a tool-backed option with an empty tool search path exits 3 with the platform link |
| Previews (stage 2) | Generated clips/frames match count, duration tolerance, resolution clamp and names |
| Cloud (stage 3) | Upload resume and idempotent re-publish against recorded fixtures; one live test-tenant run |

## Success criteria

An operator copies one `arxgo` executable (plus, optionally, `ffprobe`/`ffmpeg`) to a Linux or
Windows machine, runs `arxgo scan` to see what the archive holds, runs `arxgo split` to move every
video into a mirrored video archive on another disk, and can interrupt either run at any moment
and resume it without losing or duplicating a file. The documents-only archive can be shared
immediately; every former video location holds a video description that links to the video. Running
`arxgo restore` returns the archive to its original structure.
